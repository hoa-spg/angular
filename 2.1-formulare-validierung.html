Zwei Formular-Ansätze in Angular

Angular bietet zwei grundlegend verschiedene Wege, Formulare zu implementieren: Template-Driven Forms und Reactive Forms. Beide Ansätze sind vollständig unterstützt und in der Angular-Bibliothek als separate Module enthalten — FormsModule für Template-Driven und ReactiveFormsModule für Reactive Forms.

Das Verständnis beider Ansätze ist wichtig, da viele bestehende Angular-Projekte Template-Driven Forms verwenden, während neuere Projekte und die offizielle Angular-Empfehlung auf Reactive Forms setzen.

Vergleich der beiden Ansätze

Merkmal Template-Driven Forms Reactive Forms
Setup-Import FormsModule ReactiveFormsModule
Formular-Definition Hauptsächlich im Template (ngModel, Direktiven) Vollständig in der TypeScript-Klasse (FormBuilder)
Typsicherheit Eingeschränkt; NgForm-Objekt ist loosely typed Vollständig typisiert mit FormGroup<T>
Testbarkeit Schwieriger; Formular-State ist im DOM Sehr gut testbar; alles in reinen TypeScript-Objekten
Validierung HTML-Attribute (required, email) TypeScript-Funktionen in Validators-Array
Dynamische Felder Umständlich; erfordert *ngIf-Tricks Einfach via FormArray und addControl()
Boilerplate Wenig; gut für einfache Formulare Mehr; löhnt sich ab mittlerer Komplexität
Echtzeit-Reaktivität Möglich, aber unhandlich Eingebaut via valueChanges Observable
Empfohlen für Einfache Kontaktformulare, Login, kleine Formulare Komplexe Formulare, Wizards, dynamische Felder, Produktion
✓
Faustregel für die Wahl des Ansatzes

Template-Driven wählen, wenn: Das Formular hat wenige Felder, keine komplexe Quervalidierung, und du möchtest schnell loslegen (z.B. ein einfaches Login-Formular oder Newsletteranmeldung).

Reactive Forms wählen, wenn: Das Formular hat viele Felder, eigene Validatoren, dynamisch hinzugefügte Felder, Async-Validierung oder du die Formulardaten programmatisch verändern möchtest. Reactive Forms sind die offizielle Empfehlung für Produktionsanwendungen.

Template-Driven Forms

Bei Template-Driven Forms lebt die gesamte Formularlogik im HTML-Template. Angular's FormsModule stellt die Direktive NgModel bereit, die ein Two-Way-Binding zwischen einem Input-Element und einer Komponenteneigenschaft herstellt. Das Formular selbst wird über eine Template-Referenzvariable (#f="ngForm") im Template referenziert.

Grundprinzip: ngModel und #f="ngForm"

Einfaches Login-Formular (Template-Driven) typescript 
import { Component } from '@angular/core';
import { FormsModule, NgForm } from '@angular/forms';
import { CommonModule }       from '@angular/common';

@Component({
  selector: 'app-login',
  standalone: true,
  imports: [FormsModule, CommonModule],  // FormsModule aktiviert ngModel
  template: `
    <form #f="ngForm" (ngSubmit)="onSubmit(f)">

      <!-- ngModel = Two-Way-Binding + Formular-Registrierung -->
      <div class="form-field">
        <label for="email">E-Mail</label>
        <input
          id="email"
          name="email"
          type="email"
          ngModel
          required
          email
          #emailCtrl="ngModel"
        >
        <span *ngIf="emailCtrl.invalid && emailCtrl.touched">
          Bitte eine gültige E-Mail-Adresse eingeben.
        </span>
      </div>

      <div class="form-field">
        <label for="password">Passwort</label>
        <input
          id="password"
          name="password"
          type="password"
          ngModel
          required
          minlength="8"
          #pwCtrl="ngModel"
        >
        <span *ngIf="pwCtrl.errors?.['minlength'] && pwCtrl.touched">
          Mindestens 8 Zeichen erforderlich.
        </span>
      </div>

      <button type="submit" [disabled]="f.invalid">Anmelden</button>
    </form>
  `
})
export class LoginComponent {
  onSubmit(form: NgForm): void {
    if (form.invalid) return;
    console.log('Formulardaten:', form.value);
    // form.value = { email: '...', password: '...' }
    form.reset();
  }
}

Formular-States verstehen

Jedes Control und das gesamte Formular (NgForm) verfügt über folgende State-Flags:

Control- und Formular-States typescript 
// Gegenteilige Paare:
// pristine  ↔ dirty       (unberührt ↔ geändert)
// untouched ↔ touched     (nie fokussiert ↔ schon fokussiert/verlassen)
// valid     ↔ invalid     (alle Validatoren ok ↔ mindestens einer schlägt an)

// Zugriff via Template-Referenzvariable:
// #ctrl="ngModel"
// ctrl.pristine   → true wenn noch nie geändert
// ctrl.dirty      → true sobald Wert geändert wurde
// ctrl.untouched  → true wenn Input noch nie den Fokus hatte
// ctrl.touched    → true sobald Input den Fokus verloren hat
// ctrl.valid      → true wenn alle Validatoren bestehen
// ctrl.invalid    → true wenn mindestens ein Validator fehlschlägt
// ctrl.pending    → true wenn ein async Validator noch läuft
// ctrl.errors     → null | { required: true, minlength: {...}, ... }

// CSS-Klassen werden automatisch gesetzt:
// .ng-pristine / .ng-dirty
// .ng-untouched / .ng-touched
// .ng-valid    / .ng-invalid
ℹ
Warum auf touched prüfen?

Fehlermeldungen sollte man erst nach touched (= Nutzer hat das Feld besucht und wieder verlassen) anzeigen — andernfalls sieht der Nutzer sofort beim Laden der Seite alle Pflichtfeld-Fehler, was eine schlechte UX ist. touched signalisiert: „Der Nutzer war schon in diesem Feld und hat es verlassen.“

Reactive Forms mit FormBuilder

Reactive Forms sind der empfohlene Ansatz für komplexe Formulare in Angular. Das gesamte Formularmodell — alle Felder, ihre Initialwerte und Validatoren — wird in der TypeScript-Klasse definiert. Das Template bindet sich nur noch an dieses Modell. Das Ergebnis: typsichere, testbare, und gut wartbare Formulare.

Die Bausteine: FormControl, FormGroup, FormBuilder

FormControl und FormGroup direkt (ohne FormBuilder) typescript 
import { FormControl, FormGroup, Validators } from '@angular/forms';

// FormControl: repräsentiert ein einzelnes Eingabefeld
const nameControl = new FormControl('', [Validators.required, Validators.minLength(2)]);

// FormGroup: fasst mehrere FormControls zusammen
const form = new FormGroup({
  name:  new FormControl('', [Validators.required, Validators.minLength(2)]),
  email: new FormControl('', [Validators.required, Validators.email]),
});

// Zugriff auf Controls:
form.get('name')?.value;   // Aktueller Wert
form.get('name')?.invalid; // Validierungsstatus
form.get('name')?.errors;  // null | { required: true, minlength: {...} }

FormBuilder ist ein Service, der das Erstellen von FormGroup- und FormControl-Instanzen vereinfacht. Statt new FormControl() schreibt man einfach ein Array [initialValue, validators].

FormBuilder (kürzere Syntax) typescript 
import { inject }      from '@angular/core';
import { FormBuilder, Validators } from '@angular/forms';

// FormBuilder per inject() laden (Angular 14+):
private fb = inject(FormBuilder);

// Formular definieren (identisch zu new FormGroup, aber kürzer):
form = this.fb.group({
  name:  ['', [Validators.required, Validators.minLength(2)]],
  email: ['', [Validators.required, Validators.email]],
  // Kurzform ohne Validators:
  city:  ['Wien'],
  // Mit initialem Wert und einem einzelnen Validator (kein Array nötig):
  age:   [0, Validators.min(0)],
});

Das AddFlight-Formular — vollständige TypeScript-Klasse

Hier ist die vollständige Implementierung der AddFlightFormComponent für das FlugBoard. Sie demonstriert alle wichtigen Konzepte der Reactive Forms: Formular-Definition, Validierung, Fehlerbehandlung und Submit-Logik.

src/app/components/add-flight-form/add-flight-form.component.ts typescript 
import { Component, EventEmitter, Output, inject } from '@angular/core';
import { CommonModule }        from '@angular/common';
import {
  ReactiveFormsModule,
  FormBuilder,
  Validators,
  AbstractControl,
} from '@angular/forms';
import { CreateFlightPayload, FlightType } from '../models/flight';

// Regex: genau 2 Großbuchstaben gefolgt von 1-4 Ziffern (z.B. OS123, LH4321)
const FLIGHT_NUMBER_PATTERN = /^[A-Z]{2}\d{1,4}$/;

@Component({
  selector: 'app-add-flight-form',
  standalone: true,
  imports: [CommonModule, ReactiveFormsModule],
  templateUrl: './add-flight-form.component.html',
})
export class AddFlightFormComponent {
  // Output-Events: add sendet den neuen Flug, cancel schließt das Formular
  @Output() add    = new EventEmitter<CreateFlightPayload>();
  @Output() cancel = new EventEmitter<void>();

  private fb = inject(FormBuilder);

  // Das Formular-Modell: Felder, Initialwerte und Validatoren
  form = this.fb.group({
    flightNumber:  ['', [Validators.required, Validators.pattern(FLIGHT_NUMBER_PATTERN)]],
    airline:       ['', [Validators.required, Validators.minLength(2)]],
    type:          ['departure' as FlightType, Validators.required],
    scheduledTime: ['', Validators.required],
    expectedTime:  [''],           // Optional: kein required
    airport:       ['', [Validators.required, Validators.minLength(3)]],
    terminal:      ['T1', Validators.required],
    gate:          [''],           // Optional
  });

  // Submitted-Flag: Fehlermeldungen auch ohne touched anzeigen
  submitted = false;

  // Helper: Gibt an ob ein Fehler für ein Feld angezeigt werden soll.
  // Fehler anzeigen wenn: (touched ODER submit-Versuch) UND invalid
  showError(controlName: string): boolean {
    const ctrl = this.form.get(controlName);
    return !!(ctrl?.invalid && (ctrl.touched || this.submitted));
  }

  // Helper: Gibt die erste passende Fehlermeldung als String zurück.
  getError(controlName: string): string {
    const ctrl = this.form.get(controlName);
    if (!ctrl?.errors) return '';
    if (ctrl.errors['required'])
      return 'Dieses Feld ist ein Pflichtfeld.';
    if (ctrl.errors['pattern'])
      return 'Format ungültig — erwartet z.B. OS123 oder LH4321.';
    if (ctrl.errors['minlength']) {
      const req = ctrl.errors['minlength'].requiredLength as number;
      return `Mindestens ${req} Zeichen erforderlich.`;
    }
    if (ctrl.errors['email'])
      return 'Bitte eine gültige E-Mail-Adresse eingeben.';
    return 'Ungültige Eingabe.';
  }

  // Submit-Handler: Validierung prüfen, Daten normalisieren, Event emittieren
  submit(): void {
    this.submitted = true;
    this.form.markAllAsTouched();  // Alle Felder als "berührt" markieren

    if (this.form.invalid) return; // Abbrechen wenn Validierung fehlschlägt

    const v = this.form.getRawValue(); // Alle Werte auch von disabled controls

    this.add.emit({
      flightNumber:  v.flightNumber!.trim().toUpperCase(),
      airline:       v.airline!.trim(),
      type:          v.type as FlightType,
      scheduledTime: v.scheduledTime!,
      expectedTime:  v.expectedTime || undefined,
      airport:       v.airport!.trim(),
      terminal:      v.terminal!,
      gate:          v.gate?.trim() || undefined,
    });

    // Formular zurücksetzen — Select-Felder brauchen explizite Defaultwerte!
    this.form.reset({ type: 'departure', terminal: 'T1' });
    this.submitted = false;
  }
}

⚠
novalidate nicht vergessen

Das novalidate-Attribut am <form>-Element deaktiviert die native Browser-Validierung. Ohne es würden zwei Validierungssysteme gleichzeitig aktiv sein — das des Browsers (mit nativen Popups) und das von Angular. Angular übernimmt die Kontrolle vollständig.

valueChanges — reaktiv auf Änderungen reagieren

Einer der größten Vorteile von Reactive Forms ist das eingebaute valueChanges-Observable auf jedem Control und der gesamten FormGroup. So lässt sich z.B. das expectedTime-Feld dynamisch ein-/ausblenden:

valueChanges — reaktiv auf Eingaben reagieren typescript 
import { Component, OnInit, inject } from '@angular/core';
import { FormBuilder, Validators }   from '@angular/forms';
import { debounceTime, distinctUntilChanged } from 'rxjs/operators';

@Component({ /* ... */ })
export class AddFlightFormComponent implements OnInit {
  private fb = inject(FormBuilder);

  form = this.fb.group({
    flightNumber: ['', Validators.required],
    airline:      ['', Validators.required],
  });

  ngOnInit(): void {
    // Live-Vorschau: Flugnummer auf Großbuchstaben normalisieren
    this.form.get('flightNumber')!.valueChanges
      .pipe(
        debounceTime(200),        // Warten bis Nutzer kurz aufhört zu tippen
        distinctUntilChanged(),   // Nur reagieren wenn sich der Wert ändert
      )
      .subscribe(value => {
        if (value && value !== value.toUpperCase()) {
          // Wert ohne neue valueChanges-Emission setzen:
          this.form.get('flightNumber')!.setValue(
            value.toUpperCase(),
            { emitEvent: false }  // Verhindert rekursive Emission!
          );
        }
      });
  }
}

Eigene Validatoren schreiben

Angular's eingebaute Validators decken häufige Fälle ab. Für anwendungsspezifische Regeln — etwa „Flugnummer darf nicht mit bestimmten Präfixen beginnen“ oder „Ankunftszeit muss nach Abflugzeit liegen“ — schreibt man eigene Custom Validators.

Synchroner Custom Validator

Ein Validator ist eine reine Funktion mit der Signatur (control: AbstractControl) => ValidationErrors | null. Sie gibt null zurück wenn der Wert gültig ist, oder ein Fehler-Objekt wenn er ungültig ist.

src/app/validators/flight-number.validator.ts typescript 
import { AbstractControl, ValidationErrors } from '@angular/forms';

/**
 * Prüft ob eine Flugnummer mit einem reservierten Präfix beginnt.
 * Ungültig wenn: Wert beginnt mit 'XX' (reserviert für Testflüge).
 */
export function noTestFlightValidator(
  control: AbstractControl
): ValidationErrors | null {
  const value = (control.value as string) ?? '';

  if (value.toUpperCase().startsWith('XX')) {
    // Rückgabe: Fehler-Objekt mit Key 'reservedPrefix' und beliebigen Details
    return { reservedPrefix: { value, prefix: 'XX' } };
  }

  return null; // null = gültig
}

// form = this.fb.group({
//   flightNumber: ['', [Validators.required, noTestFlightValidator]],
// });
Fehlermeldung im Template html

    Testflüge (Prefix XX) dürfen nicht eingetragen werden.

Cross-Field Validator (Validator auf FormGroup-Ebene)

Wenn ein Validator mehrere Felder gleichzeitig lesen muss — etwa um zu prüfen, dass expectedTime nicht vor scheduledTime liegt — wird er auf der FormGroup registriert, nicht auf einem einzelnen Control:

src/app/validators/time-range.validator.ts typescript 
import { AbstractControl, ValidationErrors, ValidatorFn } from '@angular/forms';

/**
 * Gruppenvalidator: expectedTime darf nicht früher als scheduledTime liegen.
 * Wird auf FormGroup-Ebene registriert.
 */
export function timeRangeValidator(): ValidatorFn {
  return (group: AbstractControl): ValidationErrors | null => {
    const scheduled = group.get('scheduledTime')?.value as string;
    const expected  = group.get('expectedTime')?.value  as string;

    // Nur prüfen wenn beide Felder ausgefüllt sind
    if (!scheduled || !expected) return null;

    // Zeit-Strings vergleichen (HH:MM Format)
    if (expected < scheduled) {
      return { timeRangeInvalid: { scheduled, expected } };
    }

    return null;
  };
}

// Registrierung auf FormGroup-Ebene (zweites Argument von fb.group):
// form = this.fb.group(
//   {
//     scheduledTime: ['', Validators.required],
//     expectedTime:  [''],
//   },
//   { validators: [timeRangeValidator()] }  // ← auf Gruppen-Ebene!
// );
Fehleranzeige im Template (Formular-Level) html

Asynchroner Validator

Async Validators werden eingesetzt wenn die Validierung eine asynchrone Operation erfordert — etwa eine HTTP-Anfrage an den Server, um zu prüfen ob eine Flugnummer bereits vergeben ist. Sie haben die Signatur (control: AbstractControl) => Observable<ValidationErrors | null> und werden als drittes Argument beim FormControl übergeben.

src/app/validators/unique-flight-number.validator.ts typescript 
import { inject }                       from '@angular/core';
import { AbstractControl, ValidationErrors } from '@angular/forms';
import { Observable, of }               from 'rxjs';
import { delay, map, switchMap }        from 'rxjs/operators';
import { FlightService }                from '../services/flight.service';

/**
 * Async Validator: Prüft ob eine Flugnummer schon in der lokalen Liste existiert.
 * Simuliert mit delay(300) eine Server-Anfrage.
 */
export function uniqueFlightNumberValidator(
  flightService: FlightService
) {
  return (control: AbstractControl): Observable<ValidationErrors | null> => {
    const value = (control.value as string) ?? '';

    if (!value) return of(null); // Leer-Prüfung übernimmt 'required'

    return of(value).pipe(
      delay(300),  // Server-Latenz simulieren → control.pending wird true
      switchMap(flightNumber =>
        flightService.exists(flightNumber).pipe(
          map(exists => (exists ? { flightNumberTaken: { value } } : null))
        )
      )
    );
  };
}

// form = this.fb.group({
//   flightNumber: [
//     '',
//     [Validators.required, Validators.pattern(FLIGHT_NUMBER_PATTERN)], // sync
//     [uniqueFlightNumberValidator(this.flightService)]                  // async
//   ],
// });

⚠
Async Validators — Performance beachten

Async Validators werden bei jeder Änderung des Feldes aufgerufen. Ohne debounceTime würde bei jeder Tastatureingabe eine neue HTTP-Anfrage gestartet. Nutze immer debounceTime(300) (oder mehr) und switchMap, um ausstehende Anfragen automatisch abzubrechen.

Formular-State und UX

Angular verwaltet den Zustand jedes Controls und der gesamten FormGroup automatisch. Das Verständnis dieser States ist essenziell, um dem Nutzer nützliches visuelles Feedback zu geben.

State-Paar Bedeutung Typischer Anwendungsfall
pristine / dirty Wert wurde noch nie geändert / wurde geändert „Ungespeicherte Änderungen“-Warnung nur bei dirty
untouched / touched Feld hatte noch keinen Fokus / Fokus war da und weg Fehleranzeige erst ab touched (UX-Best-Practice)
valid / invalid Alle Validatoren bestehen / mindestens einer schlägt an Submit-Button deaktivieren solange invalid
pending Async Validator läuft gerade Lade-Spinner anzeigen, Submit-Button sperren
enabled / disabled Control ist aktiv / deaktiviert Felder abhängig von anderen Feldern sperren

markAllAsTouched() beim Submit-Versuch

Wenn der Nutzer den Submit-Button klickt ohne alle Felder ausgefüllt zu haben, möchte man alle Fehlermeldungen gleichzeitig anzeigen — auch für Felder, die der Nutzer nie berührt hat. Dafür gibt es markAllAsTouched():

markAllAsTouched() beim Submit-Versuch typescript 
submit(): void {
  this.submitted = true;

  // Alle Controls als 'touched' markieren:
  // → showError() gibt für jedes ungültige Feld true zurück
  // → Alle Fehlermeldungen werden sofort sichtbar
  this.form.markAllAsTouched();

  if (this.form.invalid) {
    // Fokus auf das erste ungültige Feld setzen (Barrierefreiheit):
    const firstInvalid = document.querySelector('.is-invalid') as HTMLElement;
    firstInvalid?.focus();
    return;
  }

  // Hier: Gültiger Submit → Daten verarbeiten
  this.add.emit(this.form.getRawValue() as CreateFlightPayload);
  this.form.reset({ type: 'departure', terminal: 'T1' });
  this.submitted = false;
}

setValue(), patchValue() und reset()

Formular-Werte programmatisch setzen typescript 
// setValue(): ALLE Felder müssen angegeben werden
this.form.setValue({
  flightNumber: 'OS123',
  airline:      'Austrian Airlines',
  type:         'departure',
  scheduledTime: '10:30',
  expectedTime:  '',
  airport:       'London Heathrow',
  terminal:      'T1',
  gate:          'B12',
});

// patchValue(): Nur einige Felder aktualisieren (Rest bleibt unverändert)
this.form.patchValue({
  terminal: 'T2',
  gate:     'C05',
});

// reset(): Zurück auf Initialwerte setzen
// WICHTIG: Ohne Argument werden alle Controls auf null zurückgesetzt!
// Select-Felder verlieren ihren Standardwert → explizit angeben:
this.form.reset({ type: 'departure', terminal: 'T1' });

// Einzelnes Control zurücksetzen:
this.form.get('gate')?.reset('');
ℹ
getRawValue() vs. value

form.value enthält nur Werte von aktivierten Controls — deaktivierte Controls (disabled) werden ausgeschlossen. form.getRawValue() gibt alle Werte zurück, einschließlich der deaktivierten. Im Submit-Handler ist getRawValue() in der Regel die sicherere Wahl.

Häufige Fehler

Can't bind to 'formGroup' since it isn't a known property

Die Direktive [formGroup] stammt aus ReactiveFormsModule. Dieser Fehler bedeutet, dass das Modul nicht im imports-Array der Standalone-Komponente (oder des NgModules) eingetragen ist.

Fix: ReactiveFormsModule in das imports-Array der Komponente eintragen: imports: [CommonModule, ReactiveFormsModule].

formControlName must be used with a parent formGroup directive

formControlName setzt voraus, dass ein übergeordnetes [formGroup]="form"-Element existiert. Fehlt diese Bindung am <form>-Element, weiss Angular nicht, zu welcher FormGroup das Control gehört.

Fix: Sicherstellen, dass das <form>-Element die Direktive trägt: <form [formGroup]="form" (ngSubmit)="submit()">.

Cannot read properties of null (reading 'invalid')

form.get('controlName') gibt null zurück, wenn kein Control mit dem angegebenen Namen in der FormGroup existiert. Häufige Ursache: Tippfehler im Control-Namen (z.B. 'flightNr' statt 'flightNumber').

Fix: Den Control-Namen genau prüfen. Im Template den Optional-Chaining-Operator verwenden: form.get('flightNumber')?.invalid — der ?. verhindert den Crash und gibt stattdessen undefined zurück.

Submit setzt Select-Felder nicht auf den Standardwert zurück

form.reset() ohne Argumente setzt alle Controls auf null zurück. <select>-Elemente zeigen dann keinen gewählten Wert an — oder Angular wählt den ersten Option-Eintrag, was inkonsistent ist.

Fix: form.reset() immer mit einem Objekt aufrufen, das die Standardwerte für Select-Felder (und andere Felder mit Defaultwert) enthält: this.form.reset({ type: 'departure', terminal: 'T1' }).

Aufgaben

Aufgabe 1 Flugnummer-Pattern erweitern

Das aktuelle Regex-Pattern /^[A-Z]{2}\d{1,4}$/ erlaubt nur 2-buchstabige Airline-Codes (z.B. OS, LH). Erweitere es so, dass auch 3-buchstabige ICAO-Codes erlaubt sind (z.B. AUA, DLH). Das neue Pattern soll also 2 oder 3 Großbuchstaben gefolgt von 1–4 Ziffern akzeptieren. Passe die Fehlermeldung in getError() entsprechend an (z.B. „Format ungültig — erwartet z.B. OS123 oder AUA4321“).

Aufgabe 2 timeRangeValidator implementieren und einbauen

Zeige die Fehlermeldung „Erwartete Zeit darf nicht vor der Planzeit liegen“ unterhalb des expectedTime-Feldes an — aber nur, wenn expectedTime einen Wert hat und touched ist.
