Observable vs. Promise — der vollständige Vergleich

Promises sind das bekannte Werkzeug für asynchrone Operationen: Ein Promise liefert einmal einen Wert oder einen Fehler und ist danach abgeschlossen. Observables können dagegen viele Werte über die Zeit emittieren — wie ein kontinuierlicher Strom (Stream).

Subject und BehaviorSubject

Ein Subject ist gleichzeitig Observable (man kann subscriben) und Observer (man kann mit .next() Werte hineinschicken). Es ist der Weg, um Werte manuell in einen Stream zu injizieren.

Typ Initialer Wert? Neuer Subscriber bekommt… Typischer Einsatz
SubjectNeinNichts (nur künftige Werte)Events, manuelle Trigger
BehaviorSubjectJa (Pflicht)Den letzten Wert sofortState, aktueller Filterwert
ReplaySubjectNeinDie letzten N WerteCache, History
Subject vs BehaviorSubject typescript 
import { Subject, BehaviorSubject } from 'rxjs';

// Subject – kein Initialwert, neuer Subscriber bekommt nichts
const search$ = new Subject<string>();
search$.next('Wien');          // nur aktive Subscriber bekommen 'Wien'
search$.subscribe(v => console.log(v));  // bekommt NICHT 'Wien' (zu spät)
search$.next('Berlin');        // → 'Berlin' ← dieser Subscriber kriegt es

// BehaviorSubject – hat Initialwert, neuer Subscriber bekommt letzten Wert
const filter$ = new BehaviorSubject<string>('all');
filter$.next('departure');
filter$.subscribe(v => console.log(v));  // → 'departure' sofort!
filter$.next('arrival');                  // → 'arrival'

// Wichtig: Subjects nicht direkt nach außen exponieren!
// In Services: private subject, öffentliches Observable:
export class FlightStateService {
  private searchSubject$ = new BehaviorSubject<string>('');
  readonly search$       = this.searchSubject$.asObservable(); // ← read-only!

  setSearch(term: string): void {
    this.searchSubject$.next(term);
  }
}

switchMap vs. mergeMap — der entscheidende Unterschied

switchMap: Alte Anfrage abbrechen

Wenn ein neuer Wert kommt, bricht switchMap den laufenden inneren Observable ab und startet einen neuen. Das ist der richtige Operator für Suchanfragen: Wenn der Nutzer schnell tippt, soll nur die letzte Anfrage ausgeführt werden.

mergeMap: Alle parallel

mergeMap führt alle inneren Observables parallel aus und gibt alle Ergebnisse weiter. Richtig für unabhängige Operationen wie das gleichzeitige Löschen mehrerer Flüge.

switchMap für Suchanfragen typescript 
import { Component, inject, OnInit, OnDestroy } from '@angular/core';
import { Subject, BehaviorSubject, combineLatest, interval, merge } from 'rxjs';
import {
  switchMap, map, debounceTime, distinctUntilChanged,
  startWith, catchError, takeUntil,
} from 'rxjs/operators';
import { of } from 'rxjs';
import { FlightApiService } from './services/flight-api.service';
import { Flight }           from './models/flight';

@Component({ /* ... */ })
export class FlightBoardPageComponent implements OnInit, OnDestroy {
  private flightApi = inject(FlightApiService);

  // Eingabe-Streams (Subjects):
  searchInput$  = new BehaviorSubject<string>('');
  typeFilter$   = new BehaviorSubject<string>('all');
  manualRefresh$ = new Subject<void>();

  // Ausgabe-State:
  flights:   Flight[] = [];
  isLoading: boolean  = false;
  error:     string   = '';

  // Destroy-Signal für takeUntil:
  private destroy$ = new Subject<void>();

  ngOnInit(): void {
    // Suche mit Debounce optimieren:
    const debouncedSearch$ = this.searchInput$.pipe(
      debounceTime(250),          // 250ms nach letztem Tastendruck warten
      distinctUntilChanged(),     // gleicher Wert: nicht erneut senden
    );

    // Trigger: Suche, Filter, manueller Refresh oder alle 30s
    const trigger$ = merge(
      combineLatest([debouncedSearch$, this.typeFilter$]),
      this.manualRefresh$.pipe(
        map(() => [this.searchInput$.value, this.typeFilter$.value]),
      ),
      interval(30_000).pipe(
        map(() => [this.searchInput$.value, this.typeFilter$.value]),
      ),
    ).pipe(startWith([this.searchInput$.value, this.typeFilter$.value]));

    trigger$.pipe(
      switchMap(([search, type]) => {
        this.isLoading = true;
        return this.flightApi.getFlights().pipe(
          map(flights => this.applyFilters(flights, search, type)),
          catchError(err => {
            this.error     = err.message;
            this.isLoading = false;
            return of([] as Flight[]);  // Fallback: leeres Array
          }),
        );
      }),
      takeUntil(this.destroy$),   // automatisch bei ngOnDestroy beenden
    ).subscribe(flights => {
      this.flights   = flights;
      this.isLoading = false;
      this.error     = '';
    });
  }

  ngOnDestroy(): void {
    this.destroy$.next();   // Signal senden → alle takeUntil-Streams enden
    this.destroy$.complete();
  }

  private applyFilters(
    flights: Flight[],
    search:  string,
    type:    string,
  ): Flight[] {
    return flights.filter(f => {
      if (type !== 'all' && f.type !== type) return false;
      if (!search) return true;
      const term = search.toLowerCase();
      return (
        f.flightNumber.toLowerCase().includes(term) ||
        f.airline.toLowerCase().includes(term)
      );
    });
  }
}

Memory Leaks — das takeUntil-Pattern

Wenn eine Komponente zerstört wird (Routing, *ngIf false), werden ihre Subscriptions nicht automatisch beendet. Das führt zu Memory Leaks: Die Komponente existiert noch im Speicher, weil der Observable sie noch referenziert.

takeUntil-Pattern (empfohlen) typescript 
import { Subject } from 'rxjs';
import { takeUntil } from 'rxjs/operators';

export class MyComponent implements OnDestroy {
  private destroy$ = new Subject<void>();  // Destroy-Signal

  ngOnInit(): void {
    // takeUntil: Stream beendet sich, wenn destroy$ emittiert
    someInfiniteObservable$
      .pipe(takeUntil(this.destroy$))
      .subscribe(value => this.doSomething(value));
  }

  ngOnDestroy(): void {
    this.destroy$.next();      // Signal feuern
    this.destroy$.complete();  // Subject aufräumen
  }
}
✓
async-Pipe als Alternative zu takeUntil

Die async-Pipe im Template subscribed und unsubscribed automatisch beim Zerstören der Komponente. Sie ist die einfachste Methode, Memory Leaks zu vermeiden: @if (flights$ | async; as flights) { ... }. Angular kümmert sich um den gesamten Lebenszyklus der Subscription.

Projektschritt

Projektschritt 2.3

Stream-Architektur für das FlugBoard

Refaktoriere die Lektion-2.2-Lösung auf die reaktive Stream-Architektur:

  1. searchInput$ und typeFilter$ als BehaviorSubject anlegen
  2. manualRefresh$ als Subject<void> für den Refresh-Button
  3. Suchfeld mit debounceTime(250) und distinctUntilChanged() optimieren
  4. combineLatest + merge für kombinierten Trigger-Stream
  5. switchMap für HTTP-Requests (alte Anfragen werden gecancelt)
  6. takeUntil(destroy$) in ngOnDestroy säubern
  7. Polling mit interval(30_000) hinzufügen

Häufige Fehler

ExpressionChangedAfterItHasBeenChecked

Angular erkennt, dass ein Wert sich nach dem Change-Detection-Durchlauf geändert hat (meistens durch asynchrone Operationen ohne Zone.js).

Fix: Den Wert in ngOnInit setzen (nicht im Konstruktor), oder ChangeDetectorRef.detectChanges() nach der Änderung aufrufen. Bei async-Pipe tritt dieser Fehler seltener auf.

switchMap bricht HTTP-Anfragen nicht ab

Angular's HttpClient cancelt XHR-Requests automatisch, wenn das innere Observable unsubscribed wird. Aber es gibt eine Ausnahme: Wenn der Server- Handler bereits gestartet ist, wird die Verarbeitung serverseitig nicht abgebrochen — nur der Client hört auf zu warten.

Fix (kein Bug): Das ist normales HTTP-Verhalten. switchMap verhindert, dass veraltete Antworten die UI aktualisieren. Das ist ausreichend.

Subject direkt als @Output verwendet

Subjects als @Output() zu deklarieren ist ein Anti-Pattern: der Elternteil könnte .next() von außen aufrufen.

Fix: EventEmitter für @Output() verwenden. Subjects gehören in Services oder in private Klassenfelder.

takeUntil kommt an der falschen Stelle in der Pipe

takeUntil muss an letzter Stelle in der Operator-Kette stehen. Wenn es vor catchError steht, werden Fehler nicht mehr behandelt. Wenn es vor switchMap steht, könnte der innere Observable weiterläufen.

Fix: takeUntil(destroy$) immer als letzten Operator in der pipe()-Kette platzieren, direkt vor .subscribe().

Aufgaben

Aufgabe 1 combineLatest mit Status-Filter

Erweitere den kombinierten Trigger-Stream um einen dritten Filter: statusFilter$ als BehaviorSubject<string>('all'). Nutze combineLatest([searchInput$, typeFilter$, statusFilter$]) und pass die applyFilters-Methode entsprechend an.

Aufgabe 2 Letzter Aktualisierungs-Timestamp

Nutze den tap()-Operator, um vor dem Senden jeder Anfrage einen Timestamp zu loggen und zu speichern: .pipe(tap(() => this.lastUpdated = new Date())). Zeige im Template an: „Zuletzt aktualisiert: HH:MM:SS“.

Aufgabe 3 async-Pipe implementieren

Refaktoriere die Komponente so, dass flights als Observable<Flight[]> (nicht als Array) gespeichert wird. Nutze im Template die async-Pipe: @if (flights$ | async; as flights) { ... }. Vergleiche den Code-Umfang mit der manuellen Subscription-Variante.

Aufgabe 4 forkJoin für parallele Initialisierung

Statt getFlights() allein soll beim Start gleichzeitig getFlights() und getAirports() (eine neue API-Methode, die eine Liste von Airports zurückgibt) aufgerufen werden. Nutze forkJoin([this.flightApi.getFlights(), this.flightApi.getAirports()]) und destrukturiere das Ergebnis.
